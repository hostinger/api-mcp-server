# headless-step-provision-wordpress

Create the headless WordPress backend for `<domain>` and prove it is ready. One platform call lays
every headless site out identically: WordPress in `public_html/cms`, Hostinger AI Assistant + MCP
adapter, site marked `headless`. **Out:** `site.json`.

All operations below go through the Hostinger connector (`execute`).

> **Fire vs join (background provision).** Steps 1–2 up to `hosting_websites_start-setup` are the
> **fire** half: after the setup is queued, record `provision.in_progress` and return to do prepare
> work (see the router `../SKILL.md`). The readiness **poll** at the end of Step 2, plus Steps 3–4,
> are the **join** half — run them when an instance-barrier step needs the backend (or immediately, if
> the agent can't interleave). An already-`completed` site detected in Step 1 means provision is
> already done: record `provision.completed` and adopt it.

## Step 1 — Detect before you create (never provision twice)

1. `hosting_websites_list { "domain": "<domain>" }` — substring filter, so **exact-match** the row's
   `domain`. If a row exists, note `username`, `order_id`, `website_type`.
2. `hosting_websites_list-setups { "domain": "<domain>" }` — exact-match the row:
   - `completed` → already provisioned → skip to Step 3 (adopt it).
   - `running` → skip to Step 2 (poll).
   - `failed` → tell the user and point them at hPanel; do **not** call start-setup again on your own.
3. If the site exists but `website_type` is not `headless`, stop and tell the user — this domain
   already hosts a different kind of site.

## Step 2 — Create (only when nothing exists)

1. Pick the plan: `hosting_orders_list { "statuses": ["active"] }`. One active order → use it; several
   → ask the user which.
2. Start the setup:

   ```json
   { "operation": "hosting_websites_start-setup",
     "params": { "order_id": <order_id>, "type": "headless_wordpress", "domain": "<domain>" } }
   ```

   `domain` must be a **customer-owned** domain. For a temporary `*.hostingersite.com` subdomain,
   **omit `domain`** — the setup generates one itself. Don't call a separate subdomain op to make one
   first: there's no need, and passing a generated free subdomain back as `domain` fails with
   `422 … Free subdomains cannot be provided`. The response then carries the generated domain:
   if it differs from the workspace directory name, move `~/.hostinger/<old>/` to `~/.hostinger/<new>/`,
   update the domain in `brief.md`, and tell the user the new domain.
   Admin credentials are generated by the platform; never ask the user for a password.
3. Poll `hosting_websites_list-setups { "domain": "<domain>" }` every ~15 s until `completed`
   (typically under a minute; allow a few minutes). `failed` → stop, point at hPanel.

## Step 3 — Verify (all must pass)

| Check | How | Expect |
|---|---|---|
| Site is headless | `hosting_websites_list` exact row | `website_type: "headless"` |
| WordPress at `/cms` | `wordpress_installations_list { "username": "<username>", "ownership": "all" }`, exact-match `domain` | row with `directory: "cms"`, `is_valid: true`; note its `id` |
| REST API answers | `GET https://<domain>/cms/wp-json/wp/v2/posts?per_page=1` | 200, JSON array |
| AI Assistant + MCP loaded | `GET https://<domain>/cms/wp-json/` → `namespaces` | contains `hostinger-ai-assistant/v1` and `mcp` |
| JWT mintable | `wordpress_installations_jwt-token { username, software: <id> }` | returns `token`, `mcp_url` |

Notes:

- `wordpress_installations_list` can lag a few seconds behind `completed` and return `[]` — retry
  briefly before failing. Its `domain` filter is a substring match, so exact-match the row.
- The install record's `url` may say `http://`; always use `https://` URLs.
- `GET https://<domain>/` returns 403 until the frontend is deployed — expected, not a failure.
- **Never print, log or store the JWT.** It is minted on demand (24 h lifetime) by whichever stage
  needs the per-site WP MCP; only `mcp_url` is recorded.

If a check fails: retry once after ~30 s; if it still fails, stop and point the user at hPanel.

## Step 4 — Record `site.json`

```json
{
  "backend": "wordpress",
  "website_type": "headless",
  "order_id": 1007223428,
  "username": "u…",
  "wordpress": {
    "install_id": "30…",
    "directory": "cms",
    "admin_login": "…"
  },
  "urls": {
    "site": "https://<domain>",
    "cms": "https://<domain>/cms",
    "wp_admin": "https://<domain>/cms/wp-admin",
    "rest_api": "https://<domain>/cms/wp-json/wp/v2",
    "wp_mcp": "<mcp_url from the JWT call>"
  },
  "provisioned_at": "…",
  "verified_at": "…"
}
```

No passwords or tokens in `site.json`. When the user needs wp-admin, mint a one-click link with
`wordpress_login_create-links { username, software: <install_id> }` — never hand over a password.
